1. Product overview

1.1 Vision

Make the enormous, beautiful stream of π digits explorable rather than merely impressive. A person should be able to ask a personal question — is my birthday in π? is my name? how unlikely is that? — get an answer computed from real data, understand the statistics honestly, and keep a beautiful, private memento of the result.

1.2 What the product is

π Atlas is a static web application that ships a verified dataset of the first 1,000,000,000 decimal digits of π (digits after the point, no leading 3) as same-origin binary chunks. A WebAssembly engine running inside a Web Worker scans those chunks locally. There is no server process, no account, no upload, no analytics and no paid service; the only network traffic is the app shell and the data chunks it needs.

1.3 Audience

  • Curious learners and students who want to see probability and large numbers made concrete.
  • Maths and π enthusiasts who care about verified data, positions and honest odds.
  • Social sharers who want a collectible, personalised card without giving away their query.
  • Accessibility-focused users including keyboard-only and small-screen users.

2. Goals, non-goals and use cases

2.1 Goals

  1. G1 — Search: let users search five kinds of patterns in π with live progress and cancellation.
  2. G2 — Understand: translate search difficulty into plain-English probability without overclaiming.
  3. G3 — Keep & share: produce a local, beautiful, scannable collectible card for every finished search.
  4. G4 — Include: work for keyboard, screen-reader and small-screen users.
  5. G5 — Verify: make the dataset and the build auditable, with deterministic tests and a pre-deploy smoke walk.
  6. G6 — Deploy simply: publish as static files with no server-side requirements.

2.2 Non-goals

  • Proving or implying the normality of π; odds are explicitly an idealised model.
  • Accounts, cloud storage, telemetry, advertising or server-side computation.
  • Native mobile apps; the responsive web app is the product.
  • Accepting arbitrary user-supplied datasets at runtime, or allowing network fetches outside the app's own origin.
  • Load testing or performance benchmarking of third-party deployments.

3. Functional requirements

3.1 Digits explorer

  • Accepts a digit string (1–20 digits) and reports FOUND or NOT FOUND, first position (1-based), occurrence count and surrounding context.
  • Results are row-virtualised; a minimap samples positions; occurrence navigation exposes individual matches and a 1-based position button per row.
  • Checkpoints used by tests: 12 at position 148 and 999999 at position 762 in the 2M fixture.
  • The current search is encoded in the URL (#/explore/digits?q=…) and restored on deep link.
  • A not-found result shows the closest prefix and never claims a search is impossible.

3.2 Dates explorer

  • Searches six date formats; results are shown in a format-comparison grid.
  • "Open in Number Explorer" opens a digit deep link marked d=1; privacy mode (Hide my digits) is enabled by default for these searches, with a visible note.
  • The smoke test uses 2006-09-07 and checks that no one of the six date strings leaks into the card QR or caption.

3.3 Letters explorer

  • Searches words of 1–12 letters using the app's letter encodings across two frames; results report matches in both frames.
  • Word length and encoding limits are chosen so the model stays meaningful for the dataset size.

3.4 Colours and Shapes explorers

  • Colours: paint a colour pattern and search the digit stream for the matching sequence.
  • Shapes: paint a binary shape/pattern on a grid (keyboard painting supported), use presets such as Plus, then scan with live progress and cancellation.
  • Pattern scans run off the UI thread; a "Matches in dataset" result is rendered when the worker finishes.

3.5 Probability Laboratory

An interactive view of the expected number of occurrences for a search of a given length, showing the steep drop from "everywhere" to "practically impossible". The model assumes independent random decimal digits and is described as an estimate, never as a claim about π itself.

3.6 Guided tour

Four acts, each running a real search in the app so the tour teaches by doing rather than by describing. The tour is keyboard-accessible and navigable by act; its skip control is a link (navigation semantics).

3.7 Wish Cards — Royal Observatory Plate PNGs

3.7.1 Tier rules

TierExact conditionZone-2 label / heading
Legendary (gold)found and expected < 0.01LEGENDARY · 1 IN N / "You earned a Legendary card"
Rare (silver)found and 0.01 ≤ expected < 1RARE · 1 IN N / "You earned a Rare card"
Lucky (aurora)found and expected ≥ 1LUCKY FIND / "You earned a Lucky card"
Twilightquery not foundUNCHARTED / "You earned a Twilight card"

Thresholds live in TIER_THRESHOLDS = { gold: 0.01, silver: 1 }. A non-finite or non-positive expected is treated as 1 (Lucky) with no log, so a bad statistic cannot manufacture a rare card. The tier is derived from the search result and is not user-editable.

3.7.2 Odds, copy and honesty

  • P = 1 − Math.exp(−expected); one-in-N is Math.round(1 / P), rendered by describeMagnitude (e.g. "1 million"). Odds appear only on Legendary and Rare cards.
  • Calm deterministic pools: Legendary "A rare coordinate." / "Against the odds, it is here."; Rare "Found in the stream." / "A 1-in-N coordinate."; Lucky "Found in π." / "Your place in the sequence."; Twilight "Not in this stretch of π."
  • The Uncharted tier label already names the result, so its factual line has no repeated lead. It reads, for example, Absent in the first 2,000,000 digits.
  • Every card: Odds assume random digits · Statistics, not magic.
  • The honesty banned-word guard applies to headline, subline, odds and quote; only the fine print may contain "magic". No em dashes, doubled hyphens, meme phrases or self-attributed quotes appear in user-facing copy.
  • Exactly one sourced attribution exists: "We must know. We will know." with by: "David Hilbert, 1930". No italic fonts in canvas text.
  • Copy is deterministic per search (hash of mode, query, tier and subject), so the same search always produces the same card.

3.7.3 Styles, formats and visuals

  • Both styles share one flat Royal Observatory Plate: a 1px hairline frame with registration ticks, a lowercase π ATLAS wordmark, manifest-derived edition tag, tracked tier label, centred hero with context strip, one factual line and a split QR footer.
  • collectible (default) uses the tier's royal heritage palette. clean uses a single Archival Ivory Parchment palette. The old paper style is gone.
  • No gradients, glow, sparkles, star scatter, rounded hero plates or — Pi Atlas quotes. Only the Hilbert quote is attributed. No emoji are drawn on canvas.
  • The QR code sits on a sharp archival-ivory rectangle with a 0–2px corner radius, preserving the contrast needed by jsqr. The adjacent footer text block is vertically centred on that plate.
  • Formats: Square 1080×1080, Story 1080×1920, Wide 1200×630; bottom content in Wide uses a reduced margin.
  • Theme contrast is tested: text ≥ 7:1 on both backgrounds, pill text ≥ 4.5:1, dim text ≥ 4.5:1.

3.7.4 QR, privacy and dedication

  • QR payload is the exact share URL plus src=card in the hash query; Copy link and captions never include the marker.
  • Very long payloads fall back to the mode's query-free explorer URL, dropping src, to keep the plate scannable.
  • Hide my digits removes the query from card text, context strip, QR URL, caption and filename (slug = hidden).
  • An absent context strip is left empty. Uncharted cards may show a muted Closest prefix: … line when a prefix exists; no card draws "No nearby digits available".
  • Dedication accepts Latin letters (incl. accents), digits, spaces and . - ’ & ,; collapses spaces, trims, caps at 24 characters; hint: "Latin letters only for now". It appears on the card and caption but never in the QR URL or filename.
  • QR plates: square {836,836,172}, collectible story {72,1330,220}, wide {872,120,220}, clean story {410,1300,260}.

3.7.5 Output, caption and budgets

  • Filename: pi-atlas-wish-{mode}-{slug}-{format}.png, e.g. pi-atlas-wish-digits-12-square.png.
  • Caption includes tier-aware lead, one-in-N line where relevant, "Try yours:" link and #PiAtlas #pi; dedication is inserted before the link.
  • Measured PNGs for q=12: Square 67,957 B, Story 89,626 B, Wide 47,439 B. Not-found cards: 76,206 B / 99,610 B / 55,117 B. Budgets: 1.5 / 2.2 / 1.0 MB.
  • The flat archival plate removed grain, glow and heavy texture, so every format sits far below its limit. QR payload rules and filename rules are unchanged.

3.7.6 Dev gallery

#/dev/wish renders 30 cards across tiers, formats, styles and privacy states. It draws one full-size canvas at a time, decodes each QR with jsqr, checks margins, minimum text size, story safe zone, text overlap, QR overlap and colour family, then frees the canvas (canvas.width = 0) before the next card, never more than six full-size canvases alive. It writes a smoke-report/wish-contact-sheet.png contact sheet (1216×2211). The route is compiled only in dev/E2E builds; no dev/wish string appears in production.

3.8 Sharing, history and settings

  • Deep links: every explorer search is encoded in the hash URL; copying and reopening restores the same state.
  • Shared-result banner: a scanned QR with src=card shows "Someone found … in π" with the real result; "Search your own" clears only the marker, focuses and empties the input.
  • History: a session list of recent searches with quick replay and clear.
  • Theme: system/light/dark switch, persisted locally.
  • Shortcuts: w opens the Wish Card dialog when focus is not in an input; Esc closes it and returns focus; a ? Shortcuts dialog documents both.
  • Share sheets: bottom sheets on small screens with labelled close, Escape and focus management.

3.9 Accessibility and responsiveness

  • Skip link that preserves HashRouter ownership of the hash; focuses <main> programmatically.
  • ARIA live regions for results, semantic landmarks, visible focus rings, keyboard pattern painting, reduced-motion support.
  • Axe checks on the wish-card dialog and shared-result banner (no serious/critical violations).
  • Mobile-first: compact header, bottom navigation and sheets below 768px; verified no horizontal overflow for 28 viewport×orientation pairs from 280px to 1920px.

4. System architecture

4.1 Context

The browser is the entire runtime. At build time the repository is compiled into static assets; at runtime the app fetches its own shell, WASM module and data chunks from the same origin. No component writes to a server.

Build timeTypeScript → Vite chunks; font woff2 hashed into dist/assets; WASM bindings committed; dataset packed and checksummed.
Runtime dataManifest fetch + SHA-256 verification → chunk fetch/cache → digit window and context extraction.
Runtime UIReact route + worker scan → result model → Wish Card renderer / QR / caption → download or share.

4.2 Dataset pipeline

  • Source digits: generated with y-cruncher using the Chudnovsky formula; the first 2,000,000 decimals verified against an independent mpmath computation in both the original and packaged forms.
  • Packing: decimal digits are stored 4 bits per digit in binary chunk files under public/data/pi-2m/ (local/CI default) or public/data/pi-1b/ (production). The build variable VITE_PI_DATASET_URL selects the root; the CI variable PI_ATLAS_DATASET_URL is mapped to it.
  • Each dataset tree ships web-manifest.json (camelCase, browser-facing) and core-manifest.json (snake_case, Rust/WASM), plus chunks/chunk_NNNNN.bin. The manifests record the total digit count, chunk layout and per-chunk plus whole-file SHA-256 checksums; the browser validates the web manifest at startup.
  • scripts/pack_dataset.py packs and verifies any decimal input; npm run verify:pi re-checks the committed 2M fixture.
  • Positions are 1-based decimal positions after the point; matches overlap by design.

4.3 Engine, WASM and workers

  • The committed bindings in src/generated/pi-wasm/ expose a fast scanning backend; no Rust toolchain is required in CI.
  • Pure TypeScript engines in src/engine/ are kept as parity references and are tested against the 2M fixture, alongside formatters such as formatInt, formatBig, formatMagnitude and describeMagnitude.
  • Long searches (notably pattern/scans over millions of cells) run in a Web Worker with a progress/cancel protocol so the UI remains responsive.
  • src/data/ owns the backend client, manifest store, chunk caching, digit-window extraction and context strips.

The worker protocol (workerProtocol.ts) exchanges init, job, cancel, clearCache, storageStatus and dispose requests for ready, progress, result, error and fatal responses. Job kinds are exact, letters, dates, pattern, stats, window and samples; one heavy job runs at a time and starting a new search cancels the previous one. Chunks load with 8-way bounded concurrency (mapLimit), each is checked for byte length and SHA-256 with WebCrypto before entering the engine, and progress is reported in digits checked against totalDigits. A 32-chunk LRU and an IndexedDB cache (keyed by datasetId:index) avoid repeated downloads. Chunks that leave the LRU are dropped from WASM when the last job pinning them ends, so post-scan residency stays bounded; pattern searches use the parity-tested Shift-And dispatch. Digit windows use fixed 2,048-digit buckets so the UI never receives the full digit string. API-facing DTOs translate the lean WASM results back into the original service shape, keeping the React layer independent of the engine.

4.4 Routing and state

  • HashRouter (#/…) keeps direct navigation and refresh working on GitHub Pages without rewrite rules; Vite uses a relative base for subpath hosting.
  • Query parameters encode the mode's search (q, d, etc.); src=card is a banner marker parsed strictly as a single exact value and stripped outside the Explorer.
  • Zustand stores hold ephemeral session state (history, theme); sharing state lives in the URL.
  • Because hash-only navigation does not remount the app, E2E/smoke gotoHash forces a reload between sequential searches.

4.6 Privacy and security posture

Privacy boundary. The QR is the only place src=card is added, and only when the user shares a scanned card. Captions and Copy link use the untouched share URL. Hide my digits removes the query everywhere on a card, including the file name. No cookie, analytics or third-party request is used. VITE_* variables are public by design and must never contain secrets.

Untrusted URL text is never rendered as card copy: the banner builds its text from app results, and parseSrc accepts only a single exact src=card value. Fonts are self-hosted woff2 files bundled by Vite from src/assets/fonts/.

5.3 Key algorithms and data contracts

  • Expected occurrences: (N − L + 1) / 10^L for a search of length L over N digits. This drives tier thresholds and one-in-N odds.
  • At-least-one probability: P = 1 − exp(−expected); oneIn = describeMagnitude(round(1 / P)).
  • Deterministic copy: a stable hash of the search selects from tier-specific headline, subline, quote and collector-tag pools.
  • Dedication sanitizer: allow-list regex for Latin letters with accents, digits, space and a small punctuation set; whitespace collapse, trim, 24-character cap.
  • Layout contract: TextBox rectangles with minimum font sizes; layoutBoxes plus qrPlateFor(format, style) drive both rendering and automated overlap checks.
  • QR fallback: generate at up to version 9; if the marked URL is too dense, strip parameters to the query-free explorer URL.
Disclosed discrepancy. The brief's illustrative digit-length tiers (≤8 aurora, 9–10 silver, ≥11 gold) assume a different curve from the engine's actual (N−L+1)/10^L. On the shipped 1B dataset that gives L=9 → ~1 (aurora), L=10 → ~0.1 (silver), L=12 → ~0.001 (gold). The exact threshold rules are authoritative; see decision W-D19.

6.3 Development discipline

  • Run heavy commands under a memory cap, one at a time: systemd-run --user --scope -q -p MemoryMax=3G -p MemorySwapMax=0 <command>.

  • Gallery and tests rendering many cards draw one full-size card at a time and free its canvas before the next.
  • No new runtime dependencies, network calls, analytics or emoji in canvas text.
  • Every design choice with a trade-off is recorded in DECISIONS.md.

8. Deployment and operations

  • Artifact: the static dist/ directory. Any static host works; hash routing removes the need for rewrites.
  • GitHub Pages: the workflow deploys only when PI_ATLAS_PAGES_DEPLOY=true. Its PI_ATLAS_DATASET_URL repository variable (default data/pi-2m/) is baked into the deploy build as VITE_PI_DATASET_URL; set it to data/pi-1b/ for the full site. See docs/GITHUB_PAGES_DEPLOYMENT.md and docs/BROWSER_SEARCH_ARCHITECTURE.md; DEPLOY.md is older server-era history.
  • Subpath hosting: Vite's relative base keeps assets under /pi-atlas/; HashRouter keeps deep links working on refresh.
  • Fonts: self-hosted woff2 imported from src/assets/fonts/ and hashed by Vite; no font CDN.
  • OG image: public/og.png generated locally by scripts/make_og.mjs. A Vite HTML transform rewrites og:image and twitter:image to absolute HTTPS URLs at build time using VITE_SITE_URL, falling back to the canonical Pages root when unset.
  • Secrets: none in the frontend; VITE_* values are public and must never hold tokens.
  • Smoke before deploy: npm run smoke:local then, with an explicit URL and permission, npm run smoke:live (read-only, sequential, never in parallel).
Do not put credentials in VITE_* variables: Vite embeds them in the public JavaScript bundle.

10. Limitations and future work

  • Normality of π is unproven; odds are an idealised random-digit model, never a claim.
  • Large dataset first load is dominated by same-origin transfer and verification; performance on mid-range real devices was not measured end-to-end.
  • Letter words are capped at 12 characters and patterns at the painted cell count; these bounds are documented in the UI.
  • The brief's illustrative digit-length tier boundaries conflict with the engine's expected-count curve; disclosed in W-D19.
  • Real-device testing (Android/iOS), Lighthouse scoring, foldable postures and virtual-keyboard occlusion were unavailable in headless Chromium.

Uncharted detailThe tier label is always UNCHARTED. A closest prefix is shown only as a muted context line when the card has no context strip and a prefix exists; otherwise that zone stays empty. The factual line never repeats the tier name.

10.2 Production hardening (resolved)

AreaResolution
IndexedDB write orderingChunkLoader now verifies byte length and SHA-256 first and only then calls the cache's onVerified hook. Corrupt cached bytes delete their IndexedDB key before the ChunkIntegrityError propagates, so a retry goes to the network.
WASM chunk residencyPiEngine.drop_chunk() is wired through the loader's LRU eviction hook and a per-job residency manager. Full scans still pin every chunk for require_all(), then drop all non-LRU chunks when the job ends, so post-scan residency stays at the 32-chunk JS bound.
Pattern scan implementationsearch_pattern() now dispatches to the parity-tested bit-parallel Shift-And implementation. The direct scan remains the reference; Rust unit, parity and browser E2E checks all pass.
Social unfurlsog:image and twitter:image are rewritten at build time to absolute HTTPS URLs using VITE_SITE_URL, with the canonical Pages root as a fallback.
